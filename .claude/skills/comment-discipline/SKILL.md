# Comment discipline

This codebase was generated with essay-length comments and has been trimmed once. It regrows.
**Assume any comment you are about to write is unnecessary until it passes the test below.**

## The test

Write a comment ONLY when all four hold:

1. It explains **why**, not what.
2. A competent reader **could not infer it** from the code in front of them.
3. It records something **outside the code** — the shard's behaviour, a client API quirk, an
   ordering constraint, or a bug that actually happened.
4. It fits in **one line**. Two if the fact genuinely needs it. Never more.

Fail any one and the comment does not go in. When unsure, leave it out — an absent comment costs
nothing, a wrong one costs a reader's trust in all the others.

## Hard limits

- **One line.** Two at the outside. A three-line comment needs a specific reason to exist; four
  lines is always wrong and should be cut or moved to the folder's README.
- **No file-header essays.** A module gets at most two lines saying what it is for, and most get
  none — the filename and the exports already say it.
- **No section banners.** No `// --- casting ---`, no dividers, no ASCII rules.
- **Comment density above ~15% of a file is a smell.** Above 25% means rewrite the comments, not
  the code.

## Never write these

- Restating the code. `// Leave this many behind` above `KEEP`, `// Tests only`, `// Pause between
  cycles` above `STEP_DELAY`.
- Restating a function, field or constant name as prose.
- Step-by-step narration of a block: "first we do X, then Y, then Z".
- History. "This used to be…", "the original read `x < 105`", "before the extraction…". That is
  what `git log` is for — **unless** the bug is still reachable and the comment names the concrete
  failure, in which case one line.
- Explaining language or library mechanics the reader already knows.
- Cross-references to other comments (`for the reason config.ts gives`). Reference *code*, not prose.
- TODOs about work nobody asked for.
- Restating the `it(...)` string above a test.

## What does earn a line here

These are the categories that survived the trim, and roughly the only ones:

- **Shard behaviour learned from a live run.** `0x09aa is what UOAlive uses, identified off the name`
- **Client API quirks the typings do not show.** `maxMana reads 0 before the client is told`
- **Ordering constraints.** `Before throttled: waitForTextAny returns the first match`
- **Encoding facts.** `upTo is in the client's tenths - 600 is 60.0`
- **A bug that happened, with its evidence.** `a plain assignment here threw away every stop the
  switch had just set`
- **Deliberate asymmetries** that look like mistakes. `matched for equality here, as a substring there`

Prefer to compress rather than delete these — the knowledge is the point, the wordcount is not.

## Never delete

- `/* @__PURE__ */` annotations — bundler hints, not comments.
- Anything in `types/*.d.ts` — generated by `npm run types`.
- Hex-to-name annotations on graphic tables (`0x0e75, // backpack`) — a reader cannot decode those.
- Compiler or tooling directives (`@ts-expect-error`, `eslint-disable`) if any ever appear.

## When editing existing code

Trim the comments in whatever you touch, to this standard, as part of the edit. Do not leave a
four-line essay standing next to a line you just changed.

If you add a feature, its comments are held to this policy from the first commit. A new module
arriving with a nine-line header is the failure mode this file exists to prevent.

## READMEs

The same instinct, one level up. Keep the tables, the setup steps and the "before you paste it"
lists — those are reference material. Cut the "why it exists" essays, any paragraph restating what a
table already shows, and rationale duplicated out of the code. A fact worth keeping that will not fit
in a code comment belongs here, as a bullet, not as a paragraph.

## Checking your work

```bash
# comment lines per file, worst first
for f in $(find src -name '*.ts'); do echo "$(grep -cE '^\s*//' $f) $f"; done | sort -rn | head

# a comment-only change must leave the minified bundle byte-identical
npx esbuild src/mining/index.ts --bundle --format=iife --target=es2020 --minify --outfile=/tmp/a.js
```
